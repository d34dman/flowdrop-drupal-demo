Before the numbers

Three things you should distrust about this data

Mostly n = 1

One draw per cell for most of the matrix. Where I did rerun, the same cell landed at 51 %, 71 % and 95 %. Treat every single number as one sample from a distribution of unknown width.

Retention is a byte proxy

It can't tell a faithful copy from fluent invented prose of the same length. It's a floor on damage, not a measure of fidelity.

One arm ran with no system prompt

A config bug erased it. Nothing errored. I didn't notice for hours. Those runs are marked, not deleted. More on this later, because it is the best part.

Finding 3

One line in a tool schema cost 18×.

B5  html_to_markdown(content: string)
B7  url_to_markdown(url: string)

Same agent, same model, same prompt, same pages. With B5 the model must emit the whole page as output tokens to call its tool. The page crosses the model boundary three times and is re-sent every loop. Output tokens cost 5× input and are capped by max_tokens. With B7 the argument is ten tokens, and Drupal does the fetch.

Cleanest controlled experiment in the set. A tool that takes content makes the model your transport layer. A tool that takes a handle makes it your planner. Only one of those is what you're paying for. Also: B7 made exactly 2 calls on every page on both models. B5's call count moved with the model: 3, 2, 4.

13:00 → 14:00
If the document travels through the model's output channel, how much survives is a coin flip. That's reconstruction, not copying. Take it out of the output channel and the variance disappears. The architecture, not the model, made the output reproducible. Pass a handle, let deterministic code resolve it.

Finding 4

The prompt that never arrived.

A workflow node's system-prompt port was exposed but not connected. The resolver checked array_key_exists, not emptiness, so the empty runtime input beat the configured prompt. Nothing errored. Runs completed, cost normal money, returned clean Markdown.

When an agent underperforms, prove the prompt physically arrived before you tune it.

338 tokens of prompt were worth 64 points of fidelity. The token count was the only externally visible sign anything was wrong.

The technique: put a nonsense marker like BANANA in the system prompt and assert it shows up in the model's behaviour. Before that test, I had already written up a wrong conclusion: “setting the prompt fixed it, 51 % → 93 %”. The 93 % was ordinary variance.

This is the story from the caveats slide. The research nearly concluded an architecture didn't work when the config layer had eaten the instructions. Filed upstream as flowdrop#3592438. The admission that I published a wrong conclusion lands better than any assertion, so say it plainly.

Finding 5

Architecture beats model choice. Both beat caching.

16×Architecture. Cost spread across variants on one page with one model. The cheap end is also the correct end.
12×Model. Opus ran 18 times and cost more than Sonnet 5's 46. A real lever, but it trades correctness on the cheap end.
13 %Caching. 30 % of all input tokens were verbatim repeats. Recoverable in dollars: 13 %, after the cache-write premium.

And the 13 % was unreachable anyway: the Drupal provider talks to Anthropic through the OpenAI-compatible endpoint, which accepts cache_control and silently drops it. Every one of the 170 runs shows zero cached tokens. Fixing the tool shape was worth 83 % on the same runs.

Structure first. Caching second. Model choice last.

15:30 → 17:00
Verified the caching claim against a live key: native Messages endpoint writes and reads 11,704 cache tokens; the compat endpoint returns identical prompt_tokens with no cache fields. No module-level patch possible, filed as ai_provider_anthropic#3607961. The honest hierarchy for anyone planning an AI feature budget.

Finding 6

Loud failure is cheap. Silent failure is expensive.

The good kind

Haiku 4.5 could not handle the large page in four of six agentic variants. It died at 2.0 s having spent $0.00. Visible, cheap, retryable with a different plan.

The bad kind

On the large page, a model that produced a long faithful answer overflowed the pipeline's 1 MB memory buffer after the answer was complete. The run delivered nothing. $1.90 per demonstration. Half-applied state, in the wild.

The fix for the second one is a config patch, not a model change. Any design that pushes a long answer through a loop sits near the same cliff.

17:00 → 18:00
Frontend folks: this is the same argument as optimistic UI with no rollback. Backend folks: this is a transaction that commits the expensive half and loses the cheap half. Design the boundary where the answer lands as carefully as the call that produced it.

Take this into your next AI feature

  1. Pass handles, not content.IDs, URLs, config keys. Let deterministic code resolve them. Never make the model your transport layer.
  2. Convert before the model sees it.The cheapest token is the one you never sent. 73,380 → 4,924 input tokens on the same page.
  3. Decide what “wrong” looks like before you run.A control document and assertions on content. “Completed” is a scheduler status.
  4. Prove the prompt arrived.Marker test. Watch input token counts. A prompt you can't prove arrived is one you aren't testing.
  5. Earn every loop.Start with the least agency that does the job. Add a loop only when you can measure what it buys.
  6. Budget structure, then caching, then model.16× · 13 % · 12×. In that order, and check what your provider even permits.
