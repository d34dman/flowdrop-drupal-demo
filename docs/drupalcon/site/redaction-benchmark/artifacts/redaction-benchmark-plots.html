Two variants on these charts ran without their system prompt

B5 and B5a were configured with instructions that never reached the model. FlowDrop accepts a systemPrompt on the reasoning node, but an input port that is exposed and unconnected resolves to empty and silently shadows the configured value (flowdrop#3592438). Both variants therefore describe an agent given only a URL and no instructions.

They are kept here rather than deleted, because their cost and latency are real measurements of that engine doing that work — but their fidelity should not be read as a property of the design, and the two are not distinguishable from each other: they differ only in prompt wording, so with both prompts dropped they were the same experiment run twice. That is visible in the data — 51%/51% on the small page, 44%/43% on the large.

B7 is the corrected comparison. Same ReAct engine, prompt actually applied, and one tool changed: instead of passing page content into a converter as an argument, it passes a URL and receives Markdown. On the large page that is 18× fewer input tokens and roughly a sixth of the cost, at higher fidelity.

B8 and B9, added 5 September

Same model as every other cell, one draw per page. B8 is B5's shape with the URL tool given to the parent agent — the fix B7 made, applied without changing the prompt. It lands where B7 does: exactly two calls on every page, at the same cost. B9 wraps that agent in a critic that can send the answer back up to three times. On this model the critic changed little: on the medium page it accepted the first draft (three calls, the same redactions and leaks as B8), and on the large page three revisions cut leaks from two to one at three times B8's cost and fourteen minutes of wall clock. On the small page the critic sent the draft back three times and the agent ended on the same 4,608-character document B7 and B8 produced: nine calls and five times B8's cost for an identical result at 69%. On Sonnet 5 the same design reached zero leaks on every page; here it did not.

The B9 small-page point is a rerun. The first attempt failed inside FlowDrop's loop runtime, not in the model: on the revision round the agent answered without calling a tool, and the consumer of the tool node was failed rather than skipped (flowdrop#3592443). FlowDrop fixed it the same day and the cell was rerun on the fixed module; the plotted point is that rerun.

Figure 01

What you pay against what you keep

The central tradeoff. Horizontal is cost, vertical is how much of the control's prose survives. Up and to the left is better. The control itself sits at $0 and 100% by definition — it is the ruler, not a competitor.

Both sides are normalised before comparison: link targets and image alt blocks are stripped, and runs of whitespace collapsed. Raw character count is not a fidelity metric, and the footnote below shows why it flattered and punished the wrong runs. Output that is not Markdown scores zero regardless of length — one run qualifies, ringed in red on the floor of the chart.

Each line is one variant, joining its three runs small → medium → large and labelled at the large end. Marker shape carries the page: circle small, square medium, triangle large. A red ring marks output that is not Markdown, scored zero. Hover any point for both its de-noised and its raw share.

B2 on the small page did not do the task

It returned 27,884 characters — more than the control — by handing back its own input. The output holds 665 HTML tags, 24 per thousand characters, ending in </body></html>. Asked to convert and redact in one step, the model echoed the page instead. It is scored zero: no document was produced, and length is not credit. Every other cell returned clean Markdown.

Worth dwelling on. Ranked by length alone this was the best run on the chart, sitting at 172% before the check existed. A metric that rewards a model for returning its input is not measuring fidelity, and no amount of repetition would have caught it — only reading the output did.

Fidelity falls as the page grows

Setting that failure aside, the best result keeps 102% of the small page, 87% of the medium page and 84% of the large page. The remaining losses are not redaction — they are summarising, skipped tables and dropped list items, and they get worse the more there is to reproduce. B4 clears 100% on the small page because it adds framing prose of its own, which this metric cannot tell from content.

Footnote on method: why the figures are normalised

These charts originally plotted raw character count, and the numbers were wrong in both directions. A Markdown link spends most of its characters on a URL the reader never sees, so the control's own output is padded with markup: 59% of the small page, 13% of the medium page and 51% of the large page is link targets and image alt text. A model that reproduces the prose without repeating every URL was scored as having lost half the document.

Before comparison, both the control and each run now have ](…) link targets and ![…] alt blocks removed, runs of spaces and tabs collapsed to one, and blank-line runs collapsed to one. Nothing else is touched, and the same transform is applied to both sides — the ruler is normalised exactly like the thing it measures. B3 on the large page moves from 46% to 84% under this correction; B5 and B6 from 37% to 75%.

The metric is still a proxy. It counts characters, so it cannot distinguish a dropped paragraph from a missed redaction, and it cannot tell added prose from preserved prose. It is a ceiling on fidelity, not a measure of it — the redaction and leak counts, tracked separately, are what say whether the task was done.

What the transport is not doing is losing bytes. Every job's input and output length was traced through the finished pipelines: the model's answer arrives at the output node byte-for-byte, and every run ends where the control document ends, so none of the shortfall is truncation. Every shortfall here happened inside the model.

Latency tracks what comes out, not what goes in

Two plots of the same runs. Against input tokens the points scatter with no shape; against output tokens they fall on a line. This is why the cheapest variant is often the slowest — clean input produces a longer, more faithful answer, and you wait for every token of it.

Cost per thousand characters of prose kept

Cost and fidelity folded into one number, so the ranking is not distorted by a cheap run that returned very little. Lower is better. Characters are counted de-noised, per the footnote to Figure 01 — a run is not rewarded here for echoing back link URLs.

Figure 05

Orchestration overhead against bytes persisted

The only chart here with real repetition behind it: 61 runs of workflows that call no model, so the probe was free. Overhead is wall clock minus summed node time. It does not track node count — it tracks how much FlowDrop had to serialise and store.

Fit is least squares on the 3-node control only, where node count is held constant and only payload varies.

0.220 seconds per megabyte

Plus 0.024s to start a run at all and 0.007s per additional node. Across every completed run that called a model, orchestration accounted for 0.2–1.6% of wall clock.

Reading these honestly

  • One repetition per model cell. Figures 01–04 have n=1 per point. Model latency varies run to run, so treat positions as indicative and slopes as the finding. Figure 05 is the exception, at n=61.
  • Length is a proxy, not a fidelity score. A dropped paragraph and a missed redaction both reduce it, and returning the input inflates it — as B2 small does. Outputs are checked for markup contamination, but nothing here scores whether the prose is actually correct. That needs an eval pass, which has not been run.
  • The Bench 5 large point requires a patch raising FlowDrop's memory ceiling from 1 MB to 10 MB. Unpatched, that run fails and delivers nothing.
  • All cells use claude-sonnet-4-6 and the synchronous orchestrator. No queue latency is included anywhere.
  • Filtering rescales the axes. That is deliberate — it is what makes a two-variant comparison legible — but it means absolute positions are not comparable between two different filter states. Compare shapes and orderings across filters, and read values from the tooltips.
