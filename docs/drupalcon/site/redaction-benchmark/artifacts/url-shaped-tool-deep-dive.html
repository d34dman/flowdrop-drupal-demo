FlowDrop Benchmark · Bench 7 vs Bench 5 · Sonnet 5

The URL-Shaped Tool

Two ReAct agents, same model, same system prompt, same three pages. The only difference is the shape of the tool's argument: B5's converter takes the page's HTML, so the document has to travel through the model's own output channel. B7's converter takes a URL. That one change moves the document out of the token stream — and everything downstream of it moves too.

Figure 01

Where the document actually travels

Both workflows are the same FlowDrop ReAct node with the same instructions. Both end with clean redacted Markdown. The difference is one line in a tool schema.

B5's html_to_markdown tool takes the page content as an argument, so the model must emit the entire document to call it, then read the result back in. The page crosses the model boundary three times: in as context, out as a tool argument, in again as a tool result. B7's url_to_markdown takes a URL — about ten tokens. The fetch and the conversion happen server-side in Drupal, and only the finished Markdown enters the conversation, once.

Large-page figures on the arrows. Thick strokes are the document moving as tokens; thin strokes are references. B5 pays for the page four times over the run because the ReAct loop re-sends the transcript on each iteration; B7 pays for it once.

Why the output channel is the expensive one

A tool argument is generated text. It is billed at output rates — 5× input on Sonnet 5 — it is capped by max_tokens, and it is reconstructed rather than copied, so it can drift. Passing bulk content as a tool argument makes the model a very costly transport layer for bytes it already has. A URL argument is O(1) regardless of page size; the content path becomes plain server-side code.

Figure 02

The input-token collapse

Input tokens per run, log scale. B5's line climbs steeply and then vertically — on the large page the loop took four iterations, and re-sending the transcript each time cost 1,055,106 input tokens. B7's line is nearly flat: 9,399 on the small page, 7,468 on the medium, 56,955 on the large. The large page still costs something — the converted Markdown does enter the conversation — but it enters once, not cumulatively.

Point labels are the call count the ReAct loop used for that cell. B7's medium-page input is lower than its small-page input because input here is dominated by the prompt and the converted Markdown, not by the raw HTML — the medium page is larger but converts to less prose. Hover for full numbers.

Figure 03

Cheaper and more faithful, on the same page

The usual read of an optimisation is that you trade quality for cost. This one does not. Bars are cost; markers are how much of the control document survived. On the large page B7 costs a sixth of B5 and retains more (80% against 74%). On the medium page the two are indistinguishable in fidelity — 93.2% and 93.4% — at a fifth of the price. On the small page B5's draw collapsed to a 51% summary while B7 held 94.6%.

Cost on the left axis (log, so all three pages fit); retention as a hollow marker on the right axis. Single draw per bar in this sweep — Figure 04 is what says how much a single draw can move.

What B7 does not fix: redaction accuracy

On the medium page — 36 competitor mentions in the control — B7 placed 28 marks and left 2 mentions readable; B5 placed 29 and left 1. On the large page both placed 4 and leaked none. The tool shape governs how the document moves, not how carefully the model reads it. Redaction quality is a prompting and evaluation problem, and it is still open in both architectures.

Figure 04

Three draws of one cell

The small page, Sonnet 5, run three times through each workflow. This is the finding that matters most for anything going to production, and it is invisible in a single-draw table.

B7 returned 8,715, 8,715 and 8,716 characters — 94.6% retention every time, costs within six hundredths of a cent, two calls each. B5 returned 3,721, 5,818 and 8,318 — 51%, 71%, 95% — at $0.13, $0.19 and $0.27. Same model, same prompt, same page. When the document has to survive a round trip through generated text, how much of it survives is a draw.

Small page (~38 KB), Sonnet 5, n=3 each. Left panel retention, right panel cost. B7's three markers overlap almost exactly at both. Bars behind the markers show the spread of each triple.

Figure 05

Does it hold when the model changes?

B7 was re-run end to end on Sonnet 4.6 to check whether the behaviour belongs to the architecture or to one model. It holds: two calls on every page for both models, and near-identical fidelity on the two pages that carry real content — 93.3% against 93.2% on the medium, 80.9% against 79.7% on the large. Sonnet 4.6 is slower and diverges on the small page (69% against 95%), but the shape of the run is the same. Compare that with B5 in the model matrix, where changing the model changed the call count, the cost by an order of magnitude, and in one case whether anything came back at all.

B7 only. Both models ran the identical workflow with the identical system prompt. Wall clock is the one axis that does move: Sonnet 4.6 took 327s on the large page against Sonnet 5's 225s.

Three early B7 runs are on this page but excluded from every figure

The first three B7 draws returned 30% retention and looked like a failure of the approach. They were not: they hit the same FlowDrop bug that invalidated the B5 rows — an exposed but unconnected input port resolves to empty and silently shadows the node's configured system prompt, so the agent ran with no instructions at all. Their input token count gives it away: 9,061 against 9,399 once the prompt reaches the model. They are listed in the table, marked, and excluded from Figures 01 to 05. The cost of producing this comparison

Every run in the table is real API spend. The head-to-head Sonnet 5 sweep cost $3.46, of which $2.91 was B5 and $0.55 was B7 — the benchmark itself is a small demonstration of the finding.

Reading these honestly

  • n=3 on the small page, n=1 elsewhere. The medium and large cells are single draws. Figure 04 exists precisely because a single draw of B5 can land anywhere between 51% and 95%; treat the medium and large B5 numbers as one sample from a wide distribution, and the B7 numbers as one sample from a narrow one.
  • The third draw in Figure 04 is the head-to-head run itself — the small-page cells in Figures 02, 03 and 05 are draw 3 of each triple, not a fourth independent run. Nothing is double-counted in the $3.46 total.
  • Retention is a byte proxy — de-noised identically on both sides (link targets and image alt blocks stripped, whitespace collapsed) and measured against a Bench 1 control fetch of the same URL. It cannot tell a faithful reproduction from fluent invented prose. The redaction and leak counts are what say whether the task itself was done.
  • Competitor mentions in each control: small 0, medium 36, large 5. A small-page run cannot score redactions because there is nothing to redact — its zeros are not misses.
  • Costs are metered, not estimated — read from ai_metering_usage per run via an aim_context tag, and reconciled against the Anthropic billing export. No cache reads on any row: prompt caching is unreachable through this provider (ai_provider_anthropic speaks the OpenAI-compatible endpoint, which drops cache_control).
