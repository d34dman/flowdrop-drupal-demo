Finding 01

Convert first, then ask the model

Bench 2 feeds raw HTML straight to the model. Bench 3 runs one deterministic html_to_markdown node first, then asks the model to redact. Same page, same model, same prompt intent — the node costs nothing and takes milliseconds.

Finding 02

A default is not an architecture

On the first pass the FlowDrop ReAct agent failed on the large page after ten minutes and $1.91, delivering nothing. It looked like an architectural verdict. It wasn't — it was a hard-coded constant.

Pipeline 252 · failed after 593.4s and $1.9057

2453  flowdrop_node_processor_reason      completed   out=81,803
      has_tool_calls: false   status: success   38,306 chars of finished Markdown
2454  boolean_gateway                     completed   {"active_branches":["False"]}
      the loop had already decided it was done
2455  flowdrop_node_processor_tool_invoke idle
2456  conversation_buffer                 failed
      Memory value for key "loop" in scope "pipeline" exceeds the maximum
      allowed size of 1048576 bytes (1064221 bytes given).

The agent had finished. The gateway routed the exit branch. The pipeline then died appending to a buffer nothing would read again — a 1 MB ceiling blown by bookkeeping after the answer already existed, and by only 1.5%. The text was still recoverable from flowdrop_job.output_data: 38,306 chars, both redactions, zero leaks. Correct work, thrown away.

Raised to 10 MB, the same run completes

MemoryManager::MAX_VALUE_BYTES is a class constant with no setting behind it. Patched to read flowdrop_memory.settings:max_value_bytes and raised to 10 MB, the identical run finished in 553.2s for $1.8954 and delivered 37,512 chars with both redactions and no leaks. Filed upstream as #3592436.

The matrix above reports the patched run, because the competing agent has no equivalent ceiling and comparing against an unraised default would measure a configuration choice rather than an architecture.

Worth keeping as a finding in its own right: the cost of a bad default is not a warning in a log. It is ten minutes, two dollars, and a complete answer discarded — and durable job state is the only reason anyone could tell that the answer had been complete.

Finding 03

Two engines, one task, near-identical behaviour

Bench 5 is a FlowDrop ReAct agent. Bench 6 is a Drupal AI Agent with an http_fetch tool. Same model, same prompt, same autonomy — neither is handed its page. The interesting result is how little separates them.

PageEngineCalls Tokens inCostDelivered Status

Three model calls every time, on every page size. On the large page — once the memory ceiling is out of the way — they finish 553.2s against 555.0s, and deliver 37,512 against 37,340 characters. Both caught both competitor mentions and leaked none. That is a 0.3% difference in wall clock and 0.5% in output between two unrelated agent runtimes. What the engine gives you is not the answer — it is what happens around the answer: where loop state lives, what survives a crash, and what you can measure afterwards.

Finding 04

Orchestration is not what costs you

Measured as wall clock minus the summed execution_time_us of every node. 50 runs of a graph with no model in it, so the probe itself was free. A one-node workflow establishes the floor; the three-node control, run ten times at each page size, separates per-node cost from per-byte cost.

Fixed cost of starting a run at all0.024 s
Per additional node in the graph0.007 s
Per megabyte of payload persisted0.220 s
Correlation with payload size (n=30)r = 0.931

Nodes are almost free; persistence is the whole story. Across every completed run that called a model, FlowDrop's own orchestration accounted for 0.2–1.6% of wall clock. The engine is not the bottleneck. The model is, by two to three orders of magnitude.

Method & caveats

How the numbers were produced

  • Every model call is tagged aim_context:<uuid>, which ai_metering writes to context_id. Tokens and cost are attributed by exact match, not by a time window — so runs can overlap without contaminating each other.
  • Timing comes from each job's execution_time_us (microseconds), not the second-resolution started/completed stamps.
  • Metrics are derived from stored FlowDrop state after the fact. Nothing is observed live, so any run can be re-collected for free.
  • All cells use claude-sonnet-4-6 and the synchronous orchestrator.
  • The Bench 5 large cell is the run made after patching MemoryManager to read its size ceiling from configuration and raising it to 10 MB. Every other cell is unpatched; the patch changes no default.

What these numbers do not say

  • One repetition per LLM cell. Model latency varies run to run; treat single-cell timings as indicative, not precise. The overhead figures are the exception — those are n=10 per cell.
  • Redaction counts and retention are entangled. The medium page holds 38 competitor mentions and no variant redacted more than 30 — but every variant also dropped content, so a missing redaction and a missing paragraph look alike here. Separating them needs a proper eval pass.
  • Queue latency is excluded. These runs are synchronous. In production the async orchestrator adds scheduling delay that none of this measures.
  • Nested workflows understate their own overhead, since a child pipeline's cost hides inside the parent node's execution time.
