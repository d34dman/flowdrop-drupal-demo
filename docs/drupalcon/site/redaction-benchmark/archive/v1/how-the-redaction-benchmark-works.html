How the Redaction Benchmark Works

Seven ways to do one job, wired seven different ways, measured the same way. This is the setup — the graphs, the corpus, and how tokens and time were attributed to each run so the numbers in the results can be trusted or argued with.

The corpus

Three pages, chosen for size

The span is the whole point. Variants that hand raw HTML to the model pay for the page, not for the content in it, so the cost curves only separate when the page grows. The competitor counts are ground truth, taken from the deterministic control's output — they are what a perfect run would redact.

The small page has no competitors in it

Zero redactions on the small page is correct behaviour, not a miss. It is worth saying out loud, because a redaction count read without this table looks like six variants failing at once.

The variants

Seven graphs, one job

Each is a real FlowDrop workflow, built by cloning the originals and normalising three things so they are comparable: the hard-coded URL became a declared url input port, every one runs on the synchronous orchestrator, and — where a prompt exists — the wording is identical.

Two nodes do the whole job. It has no redaction step at all, which is exactly why it is the control: its output is what a perfect conversion looks like, and its competitor mentions are what everything else is scored against. Byte-identical every run, $0.

Wired to reason, not message

The sub-workflow's documented message output port truncates the answer to about 1,003 characters — an exact prefix of the real text. The full answer is only on the reason port. Every Bench 5 run here uses reason; without that change the variant looks like it summarises, which it does not.

This is where the 1 MB ceiling lives

The conversation buffers write to pipeline memory scope, and MemoryManager::MAX_VALUE_BYTES capped that at 1 MB with no setting behind it. On the large page the transcript crossed it by 1.5% and killed the run — on the exit path, after the answer was already complete. Patched to read from configuration and raised to 10 MB for the fair comparison; filed upstream as #3592436.

Measurement

Attributing tokens and time to a run

The first version of this harness correlated model calls to runs by watching row ids before and after each launch. That works right up until two runs overlap — which happened, and produced single-call workflows recording four model calls and roughly $10 of unusable data. The rebuild removed observation entirely.

Attribution is by exact tag match, so runs may overlap safely

1

Exact cost attribution, not a time window

A small custom module tags every model call with aim_context:<uuid> on the ai.pre_generate_response event. ai_metering scans tag values and writes the uuid to context_id. Cost and tokens are then a WHERE context_id = ?, immune to concurrency.

2

Microsecond timing, not second stamps

Each job stores execution_time_us in its metadata. The started/completed fields are second-resolution, which is useless for a graph that finishes in 0.2s. Summing per-node microseconds also splits model time from graph time exactly.

3

Wall clock is the one measured number

Orchestrator overhead is wall clock minus summed node time, and it is sub-second, so it cannot come from stored stamps. One microtime() pair around launch() is recorded in the ledger. Everything else is derived.

4

Metrics are derived from stored state, after the fact

Nothing is watched live. Given a pipeline id and a context uuid, any run can be re-collected for free, days later, in any order — including runs that were launched in parallel.

# the whole loop, reduced to two commands
drush php:script launch.php  -- results bench_3_markdown_llm small,medium,large 1 my-tag
drush php:script collect.php -- results        # re-runnable, free, no side effects

Unpriced models read as free

The cost estimator defaults an unknown model's rates to zero rather than failing. A model missing from ai_metering.settings produces a complete, plausible benchmark in which every run costs exactly $0.00. Check the pricing table before trusting any cost column — including this one.

Reproducing it

What you would need

  • A DDEV Drupal site with flowdrop, ai, ai_agents and ai_metering, plus the local fd_bench module.
  • composer patches-relock && composer reinstall drupal/flowdrop — composer-patches v2 resolves from patches.lock.json, so a plain composer install silently leaves the memory patch unapplied.
  • Run as an authenticated user. drush php:script executes as anonymous, whose AI quota is a small shared ceiling that a benchmark exhausts mid-matrix.
  • Launch detached (setsid nohup) for long matrices, and let the ledger — not a terminal — be the record of what ran.

Known limits of this setup

  • One repetition per LLM cell. Model latency varies run to run; the overhead figures are the exception at n=10 per cell.
  • Redaction counts and content retention are entangled — a missing redaction and a dropped paragraph look alike until a proper eval separates them.
  • Queue latency is excluded. Every run is synchronous; production async scheduling is not measured here.
  • Nested workflows understate their own overhead, since a child pipeline's cost hides inside the parent node's execution time.
