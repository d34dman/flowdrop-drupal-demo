ReAct Redactor Deep Dive

One workflow — B5, the FlowDrop ReAct agent with tools — held fixed while the model underneath it changes: Haiku 4.5, Sonnet 4.6, Sonnet 5, Opus 5, each across the three input page sizes (small ~38 KB, medium ~164 KB, large ~535 KB of raw HTML). The workflow is identical in every cell; every difference on this page is the model.

Two failures, and only one of them is loud

On the large page Haiku's ReAct node failed after 5.8 seconds and the pipeline delivered nothing — visible, cheap, easy to catch. On the medium page it "succeeded": 69% retention, clean Markdown, wall clock and cost in the normal range — and zero redactions, with all 29 competitor mentions left in. Every health signal short of reading the output says that run worked. The loud failure costs a retry; the quiet one ships a document that wasn't redacted.

Sonnet 5's odd cells, rerun and split in two

The two low-retention Sonnet 5 cells looked like an anomaly, so both were rerun. They turned out to be two different things. The small page reproduced exactly: 52% both times, same two calls, same cost within a cent — on that page Sonnet 5 consistently returns a well-written condensation instead of a reproduction, and that is real behaviour a prompt has to pin down. The large page did not reproduce: the original draw returned 44% with zero redaction marks, the rerun returned 73% with 4 redactions — in line with Sonnet 4.6's 75% — at 269s and $1.70. The 44% cell was a bad draw, which is exactly the risk n=1 carries. Hollow markers on Figure 01 show the rerun; both observations stay on the page.

The 691k input tokens are structural, not noise

The rerun consumed 691,167 input tokens on the large page against the original's 691,024 — a 0.02% difference. Whatever the model does with its answer, the ReAct loop's habit of re-sending the whole conversation each iteration prices the large page at ~691k tokens of input for three turns, every time.

Figure 02

What the agent loop swallows

Input tokens per run, log scale. A ReAct loop re-sends its whole conversation on every iteration, so input grows with both the page and the number of turns the model takes. The models differ sharply here: on the large page, Sonnet 5's loop consumed 691k input tokens — the page re-sent across three calls — while Opus took the same page in two calls at 338k, and Sonnet 4.6 needed 503k across three. Fewer, more decisive iterations are a real cost lever, and it is the model that decides.

Input tokens, log scale. The failed Haiku large run consumed 818 tokens before dying and is plotted where it fell. Point labels show the call count the loop used for that cell.

The 4.6 large run only exists because of a patch

Sonnet 4.6's large-page cell requires raising FlowDrop's pipeline-memory ceiling from 1 MB to 10 MB (flowdrop-memory-configurable-max-value-bytes.patch); unpatched, the conversation buffer overflows after the answer is complete and the run delivers nothing. The three matrix models ran with the patch in place. Any model that pushes a long faithful answer through this workflow's loop sits near the same cliff — the fix is the patch, not the model choice.

Reading these honestly

  • One repetition per cell, except Sonnet 5 — its three cells were rerun to verify the anomaly (n=2, both observations shown). Everywhere else n=1: slopes, collapses and leak counts are the findings, and the 44%→73% swing on the rerun is the measure of how much a single draw can move.
  • Small, medium and large are input page sizes (~38 KB, ~164 KB, ~535 KB of raw HTML), never model tiers. The models are the colours.
  • Retention is a byte proxy, de-noised the same way on both sides (link targets and image alt blocks stripped, whitespace collapsed). It cannot tell a faithful reproduction from fluent added prose; the redaction and leak counts are what say whether the task was done.
  • Sonnet 4.6 rows are the original benchmark runs; the other three models come from the later matrix pass. The companion pages: the all-variant model matrix, and the original single-model plots.
