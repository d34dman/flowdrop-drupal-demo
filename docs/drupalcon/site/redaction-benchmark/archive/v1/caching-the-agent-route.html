Caching the Agent Route

How the ReAct agent route (B5) spends its input tokens today, why Anthropic prompt caching never fires, and what it takes — measured against 26 real benchmark runs — to switch it on.

Verdict. The agent route is the textbook prompt-caching workload — an append-only conversation re-sent in full every ReAct iteration — and the stack currently gets none of it. The blocker is architectural, not configurational: the Anthropic provider rides the OpenAI-compatibility endpoint through openai-php/client, and no layer from FlowDrop down to the HTTP call ever emits a cache_control block.

Modeled on the benchmark's own per-call metering rows, caching cuts input cost 34% on runs with 3+ calls (up to 50% on the deepest run) and materially cuts time-to-first-token on 330k-token prefixes. On runs that stop after one big call, naive always-on marking loses up to 25% to the cache-write premium — so the rollout needs the decision rule in §5, not a blanket flag.

None of this is speculative: the symfony/ai Anthropic bridge already ships exactly this design, enabled by default, and a sibling Drupal project running on it records live cache hits (§8). The plan below is essentially "do what that bridge does" — or adopt it.

Calls 3 and 4 each re-transmit the entire previous conversation — system prompt, tool schemas, the fetched page, and all prior turns — at full input price. Only the indigo slivers are genuinely new tokens. The same pattern holds in every multi-call run in the dataset.

Across all 26 agent-route (B5) runs in the model matrix and verification set, the route sent 4.93M input tokens, of which the recurring prefix is the overwhelming majority. Not one call recorded a cached token: cached_tokens = 0 in all 330 rows of ai_metering_usage, and the token_details blob carries only {"total": N} — the pipeline can't even see a cache hit, let alone produce one.

03Where cache_control fits

Anthropic prompt caching works on prefixes: mark up to four breakpoints in the payload, and any request within the TTL (5 minutes by default, refreshed on each hit; 1 hour available at a higher write rate) that shares a byte-identical prefix up to a breakpoint pays 10% of the input rate for those tokens. Writes cost 1.25× (5-minute TTL). The agent payload decomposes cleanly:

tools[]Static per agent config entity — identical every call, every conversation. Shared site-wide by all runs of this agent.BREAKPOINT 1
system (static part)secured_system_prompt after token substitution — stable across the conversation.BREAKPOINT 2
system (dynamic suffix)"This is the Nth time that this agent has been run." — changes every iteration. Must sit after the breakpoints or it poisons the whole cache (see Gap 3).NEVER CACHE
first big user turn (page content)The fetched page — 90%+ of tokens on large inputs, byte-stable for the rest of the run.BREAKPOINT 3
conversation prefix (turns 1…N−1)All prior assistant turns and tool results. Append-only, so last message before the newest turn is a moving breakpoint that re-uses the previous one incrementally.BREAKPOINT 4
newest turnThis iteration's tool result / user message — the only genuinely new tokens.FRESH

Within a ReAct run the iteration gap is seconds — far inside the 5-minute TTL. Two bonus effects come free: breakpoints 1–2 are shared across every invocation of the same agent site-wide, and benchmark repetitions of the same page within the TTL would share breakpoint 3 across runs. Minimum cacheable prefix is 1,024 tokens on Sonnet/Opus-tier models (Haiku tiers have a higher floor), which every breakpoint here clears except the tools+system pair on very lean agents — worth checking per agent config.

04The four gaps

Gap 1The provider can't say "cache this"

AnthropicProvider inherits chat() unmodified from OpenAiBasedProviderClientBase, which emits plain-string message content through openai-php against the compatibility endpoint. cache_control is a content-block-level field of the native Messages API; whether the compat surface passes it through is unverified, and nothing in the stack tries. The clean fix is an Anthropic-native /v1/messages path inside the provider (Guzzle is already on the base class — fetchAvailableModels() at AnthropicProvider.php:176 is the precedent), or header/field injection via OpenAI\Factory::withHttpHeader() if staying on compat proves viable.

Gap 2No cache hint survives the abstraction

ChatInput and ChatMessage (the ai module's provider-neutral message types) carry no cache-related property at all, so even a caching-aware provider has no signal for where the stable prefix ends. Short-term this is survivable — the provider sees the full message list each call and can place breakpoints heuristically (tools, system, last message before the newest turn). Long-term, a cache-hint field on ChatMessage lets ai_agents mark the boundary explicitly where it already assembles the history (AiAgentEntityWrapper.php:638–647).

Gap 3The system prompt poisons its own cache

getSystemPrompt() (AiAgentEntityWrapper.php:1108) appends a dynamic suffix containing "This is the Nth time that this agent has been run" — text that changes every iteration. Any breakpoint placed at the end of the system prompt would therefore never hit. The static secured_system_prompt must be a separately-marked block, with the loop counter (and any available_on_loop tool context) moved into an uncached trailing block — a small, upstreamable ai_agents change. The same audit applies to applyTokens() substitutions: any token that resolves to a per-request value (timestamps, session data) belongs outside the cached block.

Gap 4Metering is blind to cache economics

TokenUsageDto has a single cached (read) field, populated only from OpenAI-shape prompt_tokens_details.cached_tokens; Anthropic's native cache_creation_input_tokens / cache_read_input_tokens are never read anywhere. The good news: ai_metering is already half-ready. TokenEstimator::calculateCost() has cache_write_tokens cost math sitting unused, its provider-awareness already treats Anthropic input as cache-exclusive, and extractTokenDetails() generically sweeps all public TokenUsageDto properties into the token_details column — so adding a cacheWrite property and populating both fields in the provider closes the loop with no subscriber changes.

Latency compounds the win: cache reads sharply reduce time-to-first-token, and the deepest run spent 269 s of wall time with two ~350k-token prefixes processed from scratch.

The honest downside. A cache write that is never read back costs 25% extra. In this dataset, runs where the model answered after a single big call (all Opus 5 runs, and Sonnet 5 on small/medium pages) would have lost 21–25% on input under blanket marking — e.g. Sonnet 5 medium: $0.275 → $0.341. Two mitigations:

  • Structural: breakpoints 1–2 (tools + system) are shared across all conversations of the agent, so they amortize site-wide regardless of run depth — mark them always.
  • Probabilistic: the conversation breakpoints pay off whenever the run continues; break-even is roughly a 28% chance of a follow-up call (0.25× write premium vs. 0.9× read saving). Mark them whenever the request carries tools (a tool-use response guarantees a follow-up call), or gate on history length. In production chat — where users send multiple turns against the same buffer — the continuation probability is far higher than in these single-task benchmark runs, and the case only improves.

06Implementation plan

Phase 1 — provider-only, no upstream API changes days

  • Override chat() in AnthropicProvider with a native /v1/messages code path (Guzzle, already injected), translating the OpenAI-shape payload the base class builds.
  • Place breakpoints heuristically: cache_control: {type:"ephemeral"} on the last tool definition, the end of the system block, and the last message before the newest turn — the provider sees the full history each call, so no upstream signal is needed.
  • Apply the smart-marking rule: always mark tools+system; mark the conversation prefix only when tools are present in the request or history exceeds a threshold.
  • Feature-flag it per provider config; fall back to the compat path untouched.

Phase 2 — make the prefix cache-stable upstream, small patches

  • ai_agents: split getSystemPrompt() so the "Nth time" counter and loop-dependent context land in a trailing uncached block (Gap 3). This is the single highest-leverage upstream patch — without it, breakpoint 2 never hits.
  • ai: add an optional cache-hint to ChatMessage/ChatInput; have AiAgentEntityWrapper tag the stable boundary explicitly instead of the provider guessing.
  • flowdrop_memory: document that ConversationBuffer's sliding max_messages window invalidates the cached prefix when it trims — prefer generous windows (or trim-at-cache-boundary) for agent-backed workflows.

Phase 3 — see it in the meter observability

  • Add cacheWrite to TokenUsageDto (and treat cached as cache-read); populate both from native usage.cache_creation_input_tokens / cache_read_input_tokens in the new provider path.
  • ai_metering's generic property sweep records it automatically; TokenEstimator's dormant cache_write_rate math prices it. Surface read/write columns in the usage-log view.
  • Re-run the B5 benchmark cells to convert this study's model into measured numbers — the harness already records cached_tokens per run.

07Risks and gotchas

  • Compat-endpoint passthrough is unverified. Don't bet the design on the OpenAI-compat surface honoring cache_control; the native path is the safe route and also unlocks correct usage reporting.
  • Byte-identical means byte-identical. Tool ordering, description overrides via tool_settings, and tool_usage_limits property-hiding must be deterministic per conversation — any nondeterminism in getFunctions() output ordering silently kills breakpoints 1–2.
  • Token substitution audit. Any applyTokens() replacement in the system prompt that varies per request (time, random, session) must move out of the cached block.
  • Write premium on terminal calls caps the downside at 25% of input on that call's newly-written suffix; the smart rule in §5 bounds it further. Cache TTL (5 min, refreshed on hit) comfortably covers intra-run gaps of seconds; long-idle user chats will re-write, which is priced into the model.
  • Minimum prefix size. Prefixes under the model's floor (1,024 tokens on Sonnet/Opus tiers) are silently not cached — lean agents may see breakpoints 1–2 no-op until combined with the page turn.

08The control group: symfony/ai already does this

The same problem was checked against a sibling Drupal project (aincient-workspace/apps/cms) that runs its inference through symfony/ai-anthropic-platform 0.12 instead of the Drupal ai module. The result is a working proof of every fix this study proposes:

Gap (this stack)symfony/ai-anthropic-platform
1 · Provider can't emit cache_controlSolved, on by default. The bridge talks to the native /v1/messages endpoint, and ModelClient takes cacheRetention: 'none'|'short'|'long' — defaulting to 'short' (5-min TTL; 'long' buys the 1-hour TTL). PromptCachingTrait injects breakpoints on every request: last tool definition, last system content block, last user message.
2 · No cache hint in the message abstractionMade irrelevant. No hint is needed: in the native API, tool results arrive as user-role messages, so "mark the last user message" lands the breakpoint on the newest turn every iteration — the incremental moving-breakpoint pattern of §3, derived from payload shape alone.
3 · System prompt poisons its own cacheStill app-level. The bridge marks whatever system block it is handed; a per-request dynamic suffix (the ai_agents "Nth time" counter) would defeat it there too. The framework can't fix prompt hygiene — the cms project simply doesn't make that mistake.
4 · Metering blind to cache economicsSolved on both sides. The bridge's TokenUsageExtractor reads cache_creation_input_tokens / cache_read_input_tokens into separate fields; the cms project's UsageRecorder prices them at their opposite rates (read 0.1×, write 1.25×) instead of the combined figure.

This is not just capability on paper — the cms code carries measured evidence that caching fires in production: a first-turn agent call there reported input_tokens: 2 with cache_creation_input_tokens: 7415, i.e. Anthropic's input_tokens excludes the cached prefix entirely, and a meter that ignored the cache fields under-billed that call by ~100%. Two qualifiers carry over: the bridge marks breakpoints unconditionally, so it has the same terminal-call write-premium exposure as the naive model in §5 (its only dial is cacheRetention: 'none' per platform — no continuation heuristic); and its message breakpoint assumes the conversation prefix is append-only, the same ConversationBuffer caveat as §6.

Implication for the plan. Phase 1 has a second viable shape: instead of hand-rolling a native-API path inside AnthropicProvider, back a FlowDrop provider with symfony/ai-platform the way aincient_core does with its adapter layer — breakpoints, native usage fields, and TTL selection come with the dependency. What remains FlowDrop's to fix either way is Gap 3, which lives in ai_agents' prompt assembly, not in any transport.

09Method

Prices are the rates this environment metered at: Haiku 4.5 $1/M, Sonnet 4.6 $3/M, Sonnet 5 $2/M, Opus 5 $5/M input. The cache model treats call N's prefix as call N−1's full input (a slight under-count of the reusable prefix, since the previous call's own output also joins the prefix — the modeled savings are therefore conservative), with writes at 1.25× and reads at 0.1× of the input rate. Architecture findings were verified against module source at the file:line references cited inline; the caching-relevant greps (cache_control, ephemeral, prompt_caching, anthropic-beta) were run across web/modules/contrib/ai*, web/modules/contrib/flowdrop*, and vendor/openai-php.
